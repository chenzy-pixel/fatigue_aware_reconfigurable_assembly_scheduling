## 已确认缺陷

### F1 · P2：完成最后一道工序的动作可能被判为失败

位置：`environment/env.py:2053`、`environment/env.py:4277`。

`step()` 在执行动作及事件后，先检查决策次数上限并调用 `_apply_truncation("decision_limit")`，然后才检查全部工序是否完成。后者发现 `truncated=True` 就直接返回，无法再确认成功。

合法的一订单、一工序实例仅需两步：第一步直接加工，第二步 WAIT 到加工完成。设置 `max_decisions=2` 后实测：

```json
{
  "all_operations_done": true,
  "terminated": false,
  "truncated": true,
  "terminal_reason": "decision_limit",
  "failure_reward": -2.0,
  "unfinished_orders": 0
}
```

在仓库原始固定实例上也复现了同样问题：启发式正常完成需要 211 步；把 `max_decisions` 设为 211 后，同一条轨迹全部工序完成、未完成订单为 0，却被标记为 `decision_limit` 失败。

这会在恰好触及决策上限的成功轨迹上错误降低完成率、增加失败惩罚并改变训练目标。默认 5000 步上限下未观察到普通轨迹触发，属于已复现的边界问题。

修复方向：动作及该 tick 的全部事件处理结束后，优先判定完成；仅对仍未完成的任务应用决策上限。加入“最后一步恰好到达决策上限”的回归用例，与已有 horizon 边界测试配套。

### F2 · P2：schema-5 checkpoint 迁移后，正式网格评测的来源校验失败

位置：`agent/ppo/agent.py:483`、`result/provenance.py:219`、`eval.py:1164`、`eval.py:1216`。

`PPOAgent.load()` 为新增时间上下文输入补零后，把 metadata 的 `network_weights_sha256` 更新为 schema-6 网络哈希；`build_provenance()` 随后仍从磁盘读取原 schema-5 权重，用原始哈希与迁移后哈希比较。

基于现有迁移测试的 schema-5 合成 checkpoint 实测：加载成功，构造正式评测 provenance 时失败：

```text
checkpoint metadata network_weights_sha256 does not match the checkpoint network state
```

正式网格 CLI 在完成评测后才执行该检查，之后才创建输出目录，因此可能耗费整轮评测时间却没有落盘结果。普通单目标 CLI 重新读取原始 metadata，虽绕过此错误，却没有准确记录实际执行的迁移后网络哈希。

修复方向：分别记录、校验源 checkpoint 权重哈希与实际执行网络权重哈希，并保存迁移记录；增加“加载旧 checkpoint → 正式评测 → provenance → 写文件”的集成测试。现有测试仅验证了迁移后预测和 Adam 状态。

### F3 · P2：保存的有效配置不能直接通过标准入口重载

位置：`configs/config.py:77`、`configs/config.py:83`、`configs/runtime.py:71`、`configs/normalization.py:257`。

训练与评测通过 `public_config()` 保存 `config.json`，其中保留了自动生成的 `runtime_manifest`；标准 `load_config()` 又拒绝任何包含该字段的输入。对刚由项目保存的有效配置实测重载失败：

```text
ValueError: runtime_manifest is generated by the repository
```

因此，把某次 run 的配置快照作为 `train.py --config` 或 `eval.py --config` 输入不能直接复现。快照中的归一化清单路径还被固化为本机绝对路径，迁移到另一台机器时需要额外处理。

修复方向：明确区分用户输入配置、可重载的有效配置和只读运行身份；提供校验后重载快照的入口，保留可迁移的资源定位方式，测试配置保存/重载往返一致性。

### F4 · P1：疲劳消融编排仍绑定旧基线，无法完成当前匹配实验

位置：`scripts/run_13_evaluate_ablations.py:17`、`analysis/ablation_analysis.py:29`、`analysis/ablation_analysis.py:82`。

三组完整疲劳基线硬编码为 `*_rerun_20260928_223621`。根据 `result/runs_summary.csv`，这些历史训练使用：

| 设置 | 脚本指定的历史完整模型 | 当前无疲劳配置 |
|---|---:|---:|
| 终止失败惩罚 | 1.0 | 2.0 |
| Flow 尺度 | 1200.0 | 1152.2093959731544 |
| Cost 尺度 | 1000.0 | 386.674652792805 |
| Variance 尺度 | 50.0 | 4.937746913580247 |

这与当前实验协议要求的相同尺度、相同惩罚系数不符。上述三个目录尚在，但 `best_checkpoint.pt` 已清理；现有 run_11/run_12 也不会生成新的匹配完整疲劳单目标基线，因此按 README 顺序运行整套脚本不能完成该比较。

即使恢复旧 checkpoint，当前配置的归一化清单身份也可能触发网络兼容性检查，不能直接把旧权重解释为新协议下训练的模型。汇总脚本只核对评测单元和 dataset manifest，未验证训练惩罚、尺度、预算、输入版本等匹配条件。

修复方向：增加与当前 neutral 配置严格匹配的完整模型训练项，用实验 manifest 管理配对 run；评测前检查 checkpoint 与配置，汇总前检查全部控制变量。应在启动正式长训练前完成，避免生成无法比较的结果。

### F5 · P2：干净检出后的测试依赖未提交的 pickle 缓存

位置：`test/conftest.py:44`、`test/test_repository_contract.py:62`、`.gitignore`。

大量测试通过 `fixed_instance` fixture 直接加载 `data/instances/fixed_15x4_v1.pkl`；该文件被 Git 忽略且未跟踪。fixture 不会从已提交 YAML 构建缓存。模拟缓存不存在时，fixture 立即抛出 `FileNotFoundError`。

本机测试全通过依赖已有缓存，不等于新机器 clone 后能直接运行测试。训练主入口本身从 YAML 读取，因此不能把此项扩大解释为“训练必然无法启动”。

修复方向：测试 fixture 直接加载版本控制中的 YAML，或在测试专用临时目录生成缓存；仓库契约测试同样移除对本机历史缓存的依赖。补一次干净检出验证。
