# Schema 8 观测与即时奖励充分性审计

检查日期：2026-10-05。

结论：存在合法反例，**相同完整观测、相同合法动作，产生不同即时奖励**。
当前九维全局向量保留了累计三目标，但实际加工的工序—机器关联尚未显式进入图。

## 检查范围与方法

同一配置、同一合法算例、同一偏好 `(1/3, 1/3, 1/3)`，用两条真实的 reset/step 历史
构造状态对。逐项使用 `np.array_equal` 比较节点、边索引和属性、九维全局向量、
候选动作上下文、偏好与合法动作 mask；名称、节点 ID、决策阶段和关系方向也一致。
没有直接修改环境中的工序状态、实际分配、累计目标或事件队列。

算例沿用标准实例的 8 台机器、6 名工人及 240 分钟 horizon，包含 12 个订单、
37 道工序和三波到达。订单工序数为 3 或 4，加工时间为 8、12、14 分钟。
`validate_instance()` 通过；这是一份专门构造的合法反例，并非随机训练分布性能实验。

## 两条历史

订单 A 有 3 道工序：A1 模块加工 12 分钟，随后两道 A3 模块工序各 12 分钟。
订单 B 有 4 道工序：A1 模块加工 12 分钟，随后三道 A3 模块工序各 8 分钟。
五台 A3 兼容机器的当前加工占用持续到 t=14；因此两订单的预计最终完成时间
均为 t=38，完整链的预计裕量不能恢复当前工序的实际机器分配。

| 当前状态 t=2 | 历史一 | 历史二 |
|---|---|---|
| t=0，M1 开始加工 | A 的第一道工序 | B 的第一道工序 |
| t=2，M4 开始加工 | B 的第一道工序 | A 的第一道工序 |
| M1 / M4 的完工时刻 | 12 / 14 | 12 / 14 |
| 累计 Flow / 成本 / 承诺方差 | 14 / 0 / 0 | 14 / 0 / 0 |
| 完整观测与 mask | 完全相同 | 完全相同 |

观测哈希均为：
`477adef058c77709fcde50a29732f2f93a7abc2508379c6f6cf2f66433fd3a6b`。

## 同一动作的结果

从 t=2 执行同一个合法 WAIT（动作编号 296），时间均推进至 t=12：

| 输出 | 历史一 | 历史二 |
|---|---:|---:|
| 实际完成的工序 | A 的第一道 | B 的第一道 |
| Flow 奖励分量 | -80 | -80 |
| Cost / Variance / Failure | 0 / 0 / 0 | 0 / 0 / 0 |
| Quality 奖励分量 | -0.02114134372586382 | -0.02114134372586382 |
| Progress 奖励分量 | 0.027777777777777776 | 0.020833333333333332 |
| PPO 标量奖励 | **0.006636434051913956** | **-0.0003080103925304882** |
| terminated / truncated | false / false | false / false |

奖励差为 **1/144 ≈ 0.006944444444444444**，不是浮点舍入误差。
同一状态对的另一共同合法动作 182（派发 D 的第一道工序给 M7）产生相同奖励 0。
因此奖励差异与执行 WAIT 后隐藏的实际完工对象有关。

## 原因与修复方向

`operation_progress()` 使用按订单平衡的进度：

\[
P(s)=\frac{1}{N}\sum_j\frac{n_j^{\mathrm{done}}}{n_j}.
\]

在本例 N=12 时，完成 A 的一道工序贡献 1/(12×3)，完成 B 的一道工序贡献 1/(12×4)。
环境知道实际加工映射，因而可以确定奖励。观测中 operation 只有 PROCESSING 标志，
machine 有剩余忙碌时间，`capable_on` 表示兼容性，而 `locked_to` 只覆盖活跃重构阶段。
这些输入不能在本例确定 M1 会完成 A 还是 B。

同一 WAIT 的下一观测也不同：工序和订单节点中的状态与进度发生不同变化。
这同时给出了观测转移充分性的反例。

建议保留九维全局向量，补齐当前 PROCESSING 工序所属机器的关系。
若在现有工序—机器边增加实际加工分配标志，需要同时让该标志控制实际加工消息；
也可以增加独立的双向 processing_on 关系。随后将本例用于验证原始输入和图编码均能
区分两条历史。该建议针对已确认的缺口，仍需单独检查其他实际资源关联。

## 加工标志在当前图编码器中的作用

进一步检查发现：当前消息层对 `[邻居嵌入, 边属性]` 做单次 Linear，随后 index_add
求和并除以度数，最后才执行 LayerNorm/ReLU。若仅把标志 b 加入边属性，消息为
`W_h h + W_e e + w_b b + bias`，聚合后的标志贡献只有 `w_b × sum(b)`。

本反例交换 A/B 与 M1/M4 的加工关系，新增标志有四个位置不同；但每个工序及机器
的标志和均未改变。其他输入相同，因此精确算术下每层节点嵌入仍相同。
正在加工的工序不会成为合法派发候选，候选动作编码也无法从新增列直接取得差别。

使用同一反例、当前两层 128 维网络和五个初始化种子 0/1/11/23/37，在内存中比较：

| 编码处理 | 原始观测 | 图上下文最大绝对差（float64） |
|---|---|---:|
| 只追加 0/1 标志 | 已不同 | 4.44e-16 ～ 1.33e-15 |
| 标志同时门控双向加工消息 | 已不同 | 4.48e-5 ～ 1.49e-4 |

门控原型保持原兼容消息，并额外加入 `b × message`，以隔离乘法选择实际邻居的作用；
工序节点嵌入差为约 0.018～0.025。只加标志时的 float32 图上下文差约 2.38e-7～4.77e-7，
提高精度后降至舍入级，不能视为可靠的加工配对信息。

这些检查验证表示能力。初始化 actor 的输出仍基本相同，门控方案尚未进行训练性能验证；
不能把表示可区分直接解释为调度性能已经改善。独立 processing_on 关系可通过动态邻接
直接选择实际加工邻居，语义更清楚；保留现有关系数量时，可采用明确的加工消息门控。

`result/analysis/processing_flag_probe/report.json`。实验仅在内存中构造扩展观测及消息层。
