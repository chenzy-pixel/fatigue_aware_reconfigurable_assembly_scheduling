**D1 · P1：图观测缺少累计目标，当前奖励对观测不是 Markov 的**

位置：`environment/env.py:788–842` 的 global features；`environment/env.py:2063` 的质量差分；`environment/types.py` 的 `bounded_quality_score()`。

当前奖励依赖 `Q(J_t)-Q(J_{t+1})`，其中单目标项为 `J/(scale+J)`。累计 Flow 和累计重构成本既不在 global features 中，也没有能完整还原它们的历史完成时间/费用记录输入。已完成订单的 age 仍为当前时间减释放时间，不能还原实际完成时刻。

复现使用一个通过实例校验的微型案例：A、B 在 t=0 释放，加工时长分别为 10、30；同一机器先 A 后 B，或先 B 后 A；两者都在 t=40 完成。再等到 t=50 释放 C。

| 比较项 | 先 A 后 B | 先 B 后 A |
|---|---:|---:|
| t=50 累计 Flow | 50 | 70 |
| 节点、边、全局、偏好、动作特征 | 完全相同 | 完全相同 |
| 随后相同 C 加工及 WAIT 的末步奖励 | 0.32542702679364216 | 0.3256826314739732 |
| 最终状态 | 成功、无违规 | 成功、无违规 |

这是两条通过真实 `step()` 执行的历史，不是直接篡改累计量产生的例子。相同观测和动作无法决定当前奖励，因此无记忆 actor/critic 只能对隐藏历史求平均。在多目标非线性标量化下，历史累计目标还会影响后续目标增量之间的权衡。

建议将当前三目标累计值/一致的有界归一化值加入全局观测，确保 critic 和 actor 均能看到；同时核查决策预算等影响终止的状态量。更改需升级 observation schema、调整 checkpoint 兼容策略并重新训练。此问题不意味着现有 PPO 完全不能学习，也不能据此单独归因历史训练失败，但不能再把当前网络输入称为完整 MDP 状态。

**D2 · P2：MO-ALNS 自带正式和 smoke 配置无法通过标准入口加载**

位置：`configs/baselines/mo_alns.json:4`、`configs/runtime.py:73`、`scripts/mo_alns.py:300`、`scripts/mo_alns_benchmark.py:28`。

基线配置声明 `experiment_suite_version=mo_alns_solver_budget_v1`，但 `load_config()` 必经的 runtime 校验只接受 `single_stage_progress_quality_failure_v2`。正式和 smoke 配置实测均抛出：

```text
experiment_suite_version must match the failure-v2 reward contract
```

现有 MO-ALNS 单测主要从默认 PPO 配置中手工添加 `mo_alns` 参数，因此测试通过没有覆盖实际命令入口。

建议区分环境/奖励运行身份与算法实验协议，或让基线配置继承兼容的环境身份、另设基线协议字段；增加自带配置加载与真实 CLI 冒烟检查。

**D3 · P2：允许开启 Dropout，却未保持 PPO 采集和更新的概率分布一致**

位置：`agent/ppo/network_v8.py:102`、`:364`、`:545`；`agent/ppo/agent.py:162`、`:234`。

配置允许 `0 < dropout < 1`，图编码器和 critic 都有 Dropout。采集使用 `@torch.no_grad()`，但这不会关闭 Dropout；更新重新 forward 时会采到不同掩码，buffer 又没有存储掩码。这使存储的条件 log probability 与更新时的条件 log probability 对应不同网络随机实现。

在可接受的 `dropout=0.5` 配置下，固定相同参数、观测与动作，不执行任何优化，实测 `exp(new_log-old_log)=0.88205085`，value 从 -0.53295970 变为 -0.26799095。验证侧使用 eval 模式，还会改变实际执行的策略。

当前正式配置 `dropout=0.0`，所以现有默认实验不受这个问题影响。建议当前 PPO 先明确拒绝非零 Dropout，或在采集和优化的概率计算中一致关闭 Dropout；如果保留随机正则化，须设计相应一致性机制。`evaluate_instance()` 本身也应保证推理模式并恢复原模式。

**D4 · P3：截断的 INS 日志被计为“已完成重构”，导致密度字段自相矛盾**

位置：`environment/fatigue_monitor.py:97–109`；`environment/env.py:2558–2561`、`:4444`。

失败时 `_clip_active_log_intervals()` 把未完成 INS 的 end 裁到当前时刻，并标记 `truncated=True`。监测模块只判断 `stage=='INS' and end<=end_time`，仍把它算作完成。env.metrics 修正了 per-operation 分母/分子，却未同步修正 per-minute 指标。

固定实例在刚分配安装任务时触及决策上限，实测：时间 21.9，`completed_reconfigurations=0`，但 `completed_reconfigurations_per_minute=0.0456621`，恰好等于 1/21.9；最后一条安装日志 duration=0 且 truncated=true。

建议统一以真实 `ReconfigurationStage.DONE` 计数，或让日志审计排除 truncated 记录；两个密度字段复用同一已完成数。此项不改变训练三目标；目前共同成功集合上的消融差值也不受此失败样例影响，失败轨迹诊断与跨轨迹密度汇总会受影响。

**需要明确的两项优化/比较口径**

1. **有限失败惩罚与严格完成率优先不同。** λ=2 能保证单条成功轨迹的回报高于单条失败轨迹，却不能保证期望回报最大化始终优先提高成功概率。举例：策略 A 全成功、Q=0.9，期望回报为 0.1；策略 B 的 99% 成功轨迹 Q=0.1，1% 失败轨迹 P=0.9、Q=0.2，其期望回报为 `0.99*0.9+0.01*(-1.3)=0.878`。PPO 偏好 B，完成率优先的 selector 偏好 A。Universal 还用最差偏好完成率选模，而 PPO 聚合各偏好的期望回报。二者可以作为有意的训练代理与选模规则共存，但不能声称数学等价。若研究目标要求严格字典序或最差偏好保障，需要另行设计约束/分层目标。

2. **MO-ALNS 的“相同偏好”尚不等于主模型的相同目标。** `agent/mo_alns/types.py:25` 仍固定尺度 `(1200,1000,50)`，`archive.py:19` 使用 augmentation=1e-4 和零权重 epsilon；主模型采用冻结新尺度和 rho=0.05。等权偏好下，A=(500,100,5)、B=(500,300,1)，旧基线分数 A=0.09805508、B=0.09805737，偏好 A；当前分数 A=0.17577582、B=0.15310619，偏好 B。不同搜索目标本身可以是基线设计选择，但若要做同偏好标量性能比较，必须对齐或明确区分。`analysis/mo_alns_analysis.py` 的旧尺度和每实例 22 候选契约也不能直接用于 V8 的 66×3 预算比较。基线可保留自己的搜索策略，最终比较仍必须采用共同指标与公开预算。

**核心设计中合理的部分，以及结论边界**

- **Flow**：对已释放且未完成订单数积分，成功时等价于总完成时间减释放时间；失败时另加未完成订单惩罚。核算覆盖成功和失败案例。
- **成本**：重构阶段固定成本、机器从锁定到重构完成的停机成本、实际工人劳动成本分开累计；等待工人也算机器停机，符合当前建模。
- **负荷方差**：奖励中采用 committed load，让工人分配立即产生信号；完成不重复累计，失败将未执行的承诺工作扣回。完整成功轨迹与实际负荷方差一致。
- **疲劳**：以开工疲劳确定时长，以整个量化工期预测完工疲劳，执行中空闲工人恢复、工作完成/截断时结算。线性单调累积模型下检查完工峰值是合理的。neutral 的日志暴露是理想化时间线审计，不能解释成真实疲劳环境中的可行执行。
- **动作掩码**：生产 pair 只保证即时物理合法，可能锁入后续无法完成的重构；这与代码声明一致，不应称为保证全局可完成。若希望避免不可恢复承诺，可研究更强约束，但须同步所有方法并评估是否裁掉有效策略。
- **WAIT**：生产阶段先转交工人阶段；随后推进到外部事件、工人恢复或量化工期改善。属于显式事件驱动动作空间。最优性论断需要针对这一空间，不能仅凭 mask 通过就声称覆盖所有连续时间排程。
- **动态到达**：未来订单在 reset 已固定，其释放时间、路线及未来需求进入观测。这是有未来订单信息的释放时间调度模型；“训练在线生成实例”不等于“未知未来订单的在线调度”。如果论文要求后者，当前信息设定需调整。
- **HGNN 与专家**：打包图、类型池化、候选边上下文、偏好输入和非法动作屏蔽结构合理。固定符号/正权重保证的是 direct ranker 的局部单调性，context 和 residual 可以覆盖这一排序；整体 actor 不具有未经证明的全局目标单调性。
- **GAE 与并行**：每条轨迹独立计算后合并，不跨 episode 传播优势；真实失败/成功不 bootstrap，采集 cutoff bootstrap。当前 forced compression 关闭；开启后 γ=1 保持回报和，但 λ<1 的 GAE 衰减单位变成压缩后的决策步，不能自动宣称与未压缩训练完全等价。
- **数据分布**：非 stress 数据经过启发式完成及工期阈值筛选。这提供可行性证据，也把评测限制在“通过该规则筛选”的条件分布，不能推论所有可行排程实例。full/neutral 的预筛统一是正确的。
- **分析**：V8 前沿按实例计算，失败/超限不进入可行前沿，空可行集 HV=0；推理重复与训练种子分层汇总方向正确。seed11 消融应保持描述性结论，多次推理采样不能替代训练种子。

**仍需补齐的工程能力**

`train.py:761` 只在选模改善时保存 best，`:784` 在全部训练结束后保存 last；`:617` 的 initial checkpoint 只加载网络。尚无完整恢复 optimizer、RNG、episode 游标、selector、学习率 plateau 的 resume 路径。正式长训练建议周期性原子保存完整状态。

provenance 能检查权重、配置、数据和源码哈希，但 dirty 工作区的哈希不是可恢复的源码快照。运行末尾构造来源也可能反映运行期间修改后的磁盘代码。应在启动时冻结来源内容/patch，并在整个 run 中引用该快照。这是此前审查已指出、当前仍存在的复现能力缺口。

`validate_schedule()` 是有用的一致性检查，但主要覆盖资源重叠、先后关系和终态疲劳；不能把空列表单独当成包含释放时间、模块匹配、资格、完整加工时长和所有历史峰值的独立完整可行性证明。现有掩码、状态机和独立疲劳审计共同提供保障；建议补充面向最终日志的独立全面 checker。

**建议实施顺序**

1. 优先补齐累计目标观测，升级 schema，并加入本报告两条合法历史的回归测试。
2. 接通 MO-ALNS 配置与当前统一比较口径，验证真实入口。
