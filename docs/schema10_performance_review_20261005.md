# Schema 10 性能检查（2026-10-05）

原来的主要性能优化仍在执行，网络批处理的收益也经过本机测量确认。环境侧的候选缓存仍然有效，但候选边构造从原来的分组数组填充变成了逐边填充；新的顺序资源投影和订单链估计是当前值得优先优化的部分。

本次新增性能测量脚本和报告，未修改生产实现、训练配置或观测计算口径。

测量基线为桌面实现分支 `5ab0f10`。主线集成保留 V2 实例布局和主线冻结尺度，复现脚本从有效配置读取数据目录并使用 `agent/ppo/network.py`；本页原始数字对应测量时的实例和配置。

## 检查范围与测量方法

- 当前观测 schema 10、九维全局向量、六类节点和十四类关系。
- 使用 `configs/v8/universal.json`。隐藏宽度 128、消息传递两层、PyTorch CPU 线程数 4，训练/验证各 20 个 worker。
- 本机为 Windows 11、24 个逻辑 CPU，GPU 为 NVIDIA GeForce RTX 4060 Laptop GPU，PyTorch 2.14.1+cu132。
- 固定实例、balanced 验证实例 `instance_2000000.json`、stress 实例 `instance_5000000.json`，分别沿合法启发式轨迹采集第 0、10、20、30、40、60 步，共 18 个状态，包含生产与工人阶段。
- 冷观测在每次测量前使状态缓存失效；热观测反复读取同一状态。均预热，取重复测量的中位数。
- 网络比较当前模型的 `reference_v8` 与默认 `phase_batched_v1` 执行路径，使用相同参数、观测和 mask，并检查 logits/value 数值一致。GPU 每次测量前后同步，计时包括图打包和数据传输。

这里测量的是组件耗时，不是完整训练吞吐。参考网络也是当前 schema 10 模型，不能将其理解成修改前后整个项目的耗时对比。采样覆盖轨迹前段，不能代替所有实例和所有阶段的性能评估。

| 优化 | 当前状态 | 证据 |
|---|---|---|

| 在线训练实例跳过反事实分类 | 生效 | 在线生成设置 `classify_reconfiguration_value=False`；持久化基准仍保留分类 |

## 本机测量

### 环境观测

| 实例 | 新状态首次构造 | 同一状态缓存读取 |
|---|---:|---:|
| 固定实例 | 42.16 ms | 0.065 ms |
| balanced 验证实例 | 51.48 ms | 0.081 ms |
| stress 实例 | 50.42 ms | 0.074 ms |

冷 mask 为 1.24–1.66 ms，缓存 mask 约 0.00025–0.00035 ms。缓存收益明显，但每次动作改变状态后仍需要新的计算；不能将同一状态缓存读取的加速倍数作为整段 rollout 的加速倍数。

|---|---:|---:|---:|---:|
| CPU | 1 | 6.40 ms | 5.15 ms | 1.24× |
| CPU | 8 | 31.74 ms | 16.18 ms | 1.96× |
| CPU | 20 | 81.22 ms | 23.89 ms | 3.40× |

batch 20 图打包耗时：CPU 从 5.40 ms 降到 0.85 ms，GPU 从 25.52 ms 降到 1.70 ms。仅 critic 求值分别为 CPU 18.58 ms、GPU 11.60 ms，低于各自的完整前向。

本次小图、batch 20 的完整前向中，CPU 比 GPU 略快；critic 则是 GPU 更快。PPO 反向传播和真实并行采样未在这里比较，不能据此决定整轮训练改用 CPU。

## 当前热点与优化顺序

18 次冷观测的 cProfile 显示：

| 函数 | 调用次数 | 累计时间 |
|---|---:|---:|
| `ResourceProjector.transition` | 15,992 | 1.434 s |
| `OrderTimeEstimator.finish_ticks` | 35 | 1.280 s |
| `ResourceProjector.stage_options` | 31,723 | 1.087 s |
| `_build_capability_relation` | 18 | 0.979 s |
| `ResourceProjector.path_costs` | 6,666 | 0.197 s |
| `np.var` | 13,286 | 0.173 s |
| `ProjectedResources.copy` | 123,812 | 0.167 s |
| `np.clip` | 33,330 | 0.162 s |

累计时间存在包含关系，不能相加；性能分析器也会增加开销。订单链估计既服务当前状态，也服务假设 WAIT 后的状态，所以 18 个状态会触发 35 次估计。

建议按以下顺序优化：

1. **复用相同顺序投影。** 诊断、候选边和订单链会请求部分完全相同的 transition。本次按环境/状态版本、当前时刻、机器、源/目标模块、最早时刻、全部工人可用时刻与疲劳、承诺负荷统计，15,992 次请求中有 3,193 次输入重复，约 19.97%。可增加状态内的纯投影缓存，或统一由投影上下文提供。缓存返回值需要保持分支独立。重复请求比例不等于最终加速比例，缓存键构造和复制也有成本。
2. **恢复便宜特征的数组计算。** 候选路径按正确语义分组计算，路径的固定费、人工费、停机费和方差增量每个共享路径计算一次；加工时间、归一化、裁剪和列填充批量完成。当前每条边都调用 `path_costs()` 并进行多次标量 `np.clip`，这部分不需要重复枚举完整路径。
3. **减少投影分支的复制和重复查找。** 每状态复用初始资源快照，预先索引模块的合格工人；阶段搜索先生成时刻/疲劳结果，只为需要继续搜索的分支物化资源数组。必须保留完整 DIS→INS 枚举、疲劳延续、确定性并列规则和选定路径的成本/方差口径。
4. **再测 worker 数和强制动作压缩。** 当前 20 个 worker 加主进程 4 个 PyTorch 线程，并不意味着增加 worker 就会更快。应在一致采样预算、配置和硬件下比较完整采样/更新/验证耗时。强制动作压缩在当前代码要求 `gamma=1`，且涉及强制动作段的采样和 GAE，需要独立验证后启用。

第一至第三项可以保持 schema 10 的状态语义。验收应逐字段对比优化前后的观测、mask、物理轨迹、奖励及累计目标，覆盖忙碌机器、实际活动重构、同一工人连续服务、不可达路径、跨期限和外部截断，再复测耗时。
